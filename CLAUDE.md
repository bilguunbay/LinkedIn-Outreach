# PART 1: PROJECT CONTEXT

## Project Summary

A Chrome Extension that sends personalized LinkedIn messages on the user's behalf using AI-generated copy and Playwright-driven browser automation. The user uploads a CSV of contacts, writes a base template plus personalization instructions, reviews AI-generated previews, and approves them before any sending happens. A local Node.js process running Playwright performs the actual sends in the user's real Chrome browser, mimicking human behavior closely enough to stay under LinkedIn's automation detection thresholds.

**The single most important constraint: account safety over everything.** Any decision that conflicts with anti-detection requirements loses. Throughput, convenience, shipping speed, code elegance — none of these override account safety. If a feature would let the user send faster but increases ban risk, it does not ship.

---

## Standing Engineering Rules

These rules apply to every file in this codebase, including code generated by AI assistants. They are not aspirations.

1. **DRY.** No duplicated logic, markup, styling, or behavior across components. The default action when adding functionality is to extend an existing component or function — never to create a parallel one with overlapping responsibilities.
2. **No hardcoded values** (after the first scaffold pass). Colors, spacing, timings, limits, copy strings, selectors, endpoints, retry counts — all reference a named token or config entry from a single source of truth.
3. **Tokens and components, always.** Visual primitives flow through `tokens.json`. Logic primitives flow through typed modules in `config/`. UI is composed from `components/` — never one-off markup that duplicates a base component pattern.

Enforcement: a pre-commit lint step rejects hex colors, magic numbers in known ranges, inline DOM selector strings outside `config/selectors.ts`, and any user-facing string outside `config/copy.ts`.

## Tech Stack

| Layer | Choice | Notes |
|---|---|---|
| Extension UI | Chrome Extension Manifest V3 (HTML/CSS/JS) | Popup + side panel; no host permissions for linkedin.com |
| Browser automation | Playwright (Node.js) | Launched via `channel: 'chrome'` — never bundled Chromium |
| Extension ↔ host comms | Chrome Native Messaging | Length-prefixed JSON over stdio |
| AI | Anthropic or OpenAI API | Called from the extension side, not the native host |
| CSV parsing | PapaParse | Client-side only; CSV never leaves the machine |
| Persistence | `chrome.storage.local` (settings, templates, counters) and `chrome.storage.session` (API key when user opts in) | Plaintext storage — see security note in Part 1 §Security |
| Browser binary | Real Google Chrome via `channel: 'chrome'` | Refuses to launch if Chrome is not installed |

**Non-negotiables:**
- `headless: false` always
- `channel: 'chrome'` always (no bundled Chromium fallback)
- Messages typed via `page.type()` with randomized per-keystroke delay — never `page.fill()` or clipboard paste
- The extension declares zero host permissions for LinkedIn; all LinkedIn DOM interaction happens in the Playwright window, not the user's main browser

## Architecture Overview

### Communication Topology

```
┌──────────────────────┐       Native Messaging        ┌─────────────────────┐
│  Chrome Extension    │ ◄──── (length-prefixed JSON ────► │  Node.js Native     │
│  (popup + bg worker) │           over stdio)         │  Host (Playwright)  │
└──────────┬───────────┘                               └──────────┬──────────┘
           │                                                       │
           │ HTTPS                                                  │ Playwright
           ▼                                                       ▼
   ┌──────────────┐                                       ┌────────────────┐
   │  AI Provider │                                       │  Real Chrome   │
   │  (Anthropic/ │                                       │  Browser Window│
   │   OpenAI)    │                                       │  → linkedin.com│
   └──────────────┘                                       └────────────────┘
```

- **The extension** owns the UI, CSV parsing, AI calls, settings, and orchestration.
- **The native host** owns Playwright, the browser, and all LinkedIn DOM interaction.
- **The two never share state directly** — every cross-boundary action goes through a typed message defined in `config/protocol.ts`.

### Data Flow (full campaign)

1. **Upload** — User drags CSV → `csvParser.js` validates → renders rows in `views/CampaignSetup.js`
2. **Configure** — User writes template + personalization instructions → saved to `chrome.storage.local`
3. **Generate** — `aiClient.js` calls AI for each row (5 concurrent) → previews rendered as `PreviewCard` components
4. **Approve** — User approves / edits / regenerates / skips per card → approved set goes to send queue
5. **Connect** — Extension calls `nativeHostClient.connect()` → spawns native host → handshake (`ping` / `pong`)
6. **Send** — Extension sends `start_campaign` with approved contacts + settings → host begins send loop
7. **Loop** — For each contact: navigate → scroll → classify button state → either send or skip with reason → log → wait randomized delay → next
8. **Stream** — Host emits `contact_started`, `contact_result`, `warning_detected`, `session_expired` messages → `views/SendQueue.js` updates live
9. **Halt or finish** — Queue completes, hits a cap, hits a warning, or user stops → host shuts down
10. **Export** — User clicks Export Results → `logger.js` builds the result CSV from accumulated logs → download

### Why AI Calls Live in the Extension, Not the Host

The extension already holds the user's API key and manages user-facing flows (preview, edit, regenerate). Putting AI calls in the host would require duplicating the key in two places, complicating the regenerate-per-card flow, and adding an unnecessary round trip. The host has one job: drive the browser safely.

## Key Rules for Every Coding Session

These are non-negotiable. If a generated implementation violates any of them, reject it and regenerate.

- [ ] **Use async/await everywhere.** No callbacks, no `.then()` chains in new code.
- [ ] **Real Chrome only.** Every Playwright launch goes through `native-host/browserFactory.js`, which sets `channel: 'chrome'`. No other launch sites.
- [ ] **Headful only.** `headless: false` is enforced in `browserFactory.js` and may not be overridden anywhere.
- [ ] **Type, never fill.** The message input is populated only via `humanize.typeMessage()`, which uses `page.type()` with randomized per-keystroke delay. No `page.fill()` and no clipboard paste anywhere near message content.
- [ ] **No URL outside the CSV.** The host navigates only to `linkedin_url` values from the user's CSV. No search, no suggested connections, no "people also viewed."
- [ ] **Check for warnings after every navigation.** `warningDetector.check(page)` runs after every nav, before any other action. On detection, the queue halts immediately.
- [ ] **Halt means halt.** Never attempt to "continue past" a warning. Never auto-resume after a halt of any kind.
- [ ] **Caps before every send.** `rateLimiter.canSend()` is the gate; no send call bypasses it. Daily and weekly counters are read from `chrome.storage.local` (the source of truth) and respected by the host.
- [ ] **All delays randomized.** No fixed `setTimeout(fn, 1000)` patterns. Every delay reads its range from `config/timing.ts` and uses the `humanize.randomDelay(range)` helper.
- [ ] **Log before moving on.** Every attempt — sent, skipped, failed — is persisted via `logger.recordAttempt()` before the next contact begins. No batched "log at end" patterns; a crash mid-campaign must not lose result data.
- [ ] **Tokens and config, never magic values.** Reviewing your own code: if you see a number, hex code, selector string, or user-facing string inline anywhere outside `tokens.json` / `config/`, move it.
- [ ] **Extend, don't duplicate.** Before creating a new component or helper, search for an existing one with overlapping responsibility. If found, extend it.

## Selector Strategy

LinkedIn changes its DOM regularly. Selectors are infrastructure, not implementation detail.

- **Single source:** All LinkedIn selectors live in `config/selectors.ts`. Logic files import named selector arrays — they never contain selector strings.
- **Fallback arrays:** Every critical element has **at least 3 fallback selectors** in priority order. Example shape:

  ```ts
  // config/selectors.ts
  export const MESSAGE_BUTTON = [
    'button[aria-label^="Message"]',                  // primary
    'button.message-anywhere-button',                 // class fallback
    'main button:has-text("Message")',                // text fallback
  ] as const;
  ```

- **Resolution helper:** A single `resolveSelector(page, selectorList)` helper in `native-host/sender.js` walks the array and returns the first match. Logic files call this helper, never `page.locator()` directly with a string.
- **On selector miss:** log the miss with full context (which selector list, which contact), classify the contact appropriately (most often `messaging_disabled` or push to a manual review bucket), skip, and continue. Never guess. Never attempt the action with a "similar-looking" element.
- **Health check:** `selectorHealth.js` runs on the **first contact of every campaign**. It loads that contact's profile and verifies that every critical selector list (Message button, message dialog, message input, send button) resolves to at least one element. If any list fails, the campaign halts before sending anything, with a clear "selectors out of date" message.
- **Updates without rebuilds:** `config/selectors.ts` is structured so a user can update it from a published gist URL (manual paste, no auto-update mechanism) without rebuilding the extension.

## Message Button State Classifications

Every contact resolves to exactly one of four states. Each has a dedicated handling path and log classification — none are treated as generic failures, and only the first counts against the daily/weekly caps.

| Detected State | Meaning | Tool Behavior | Log Classification | Counts Against Cap? |
|---|---|---|---|---|
| Standard **Message** button | 1st-degree connection | Proceed with send | `sent` (or `failed` if send itself errors) | ✅ Yes |
| **Send InMail** button | Out of network; paid InMail required | Skip; do not consume InMail credit | `inmail_required` | ❌ No |
| No messaging button at all | Profile owner disabled messaging | Skip | `messaging_disabled` | ❌ No |
| **Connect** button only | Not connected | Skip | `not_a_connection` | ❌ No |

Plus two non-button states:

| State | Classification | Counts Against Cap? |
|---|---|---|
| Profile fails to load (404, redirect to feed) | `profile_unreachable` | ❌ No |
| Redirect to login or checkpoint | `session_expired` (and halts the queue) | ❌ No |

All classifications are defined as enums in `config/classifications.ts`. Logic files reference the enum, never the string literal.

## Security Notes (Read Every Session)

- **AI API key** is stored in `chrome.storage.local` by default, which is **plaintext on disk**. The user sees a one-time warning when they enter it. Offer `chrome.storage.session` as an opt-in for stronger isolation.
- **LinkedIn auth state** (storageState) is written to the OS user data directory with `0600` permissions on Unix.
- **Nothing leaves the machine** except: AI API calls and the actual messages sent to LinkedIn. No telemetry, no error reporting, no analytics in v1.
- **API key is never logged, never exported, never included in any CSV or log file.** Add this assertion to `logger.js` as a hardcoded key-name blocklist.
